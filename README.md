# aws-sensor-data-quality-pipeline

A data engineering pipeline for ingesting, validating, cleaning, and analyzing
multi-device IoT sensor time-series data. Built local-first in Python, with an
optional, cost-gated AWS execution path (S3 / Glue / Athena) for anyone who wants
to see the same pipeline run against managed cloud services.

## Why synthetic data

This project is inspired by a real sensor data-quality exercise, but **the dataset in
this repo is entirely synthetic** - generated by a deterministic, seeded script
(`scripts/generate_sample_data.py`), not copied or derived from any company's actual
data. The *kinds* of problems it contains (duplicate records, a mislabeled unit, a
malformed timestamp format, a stuck sensor, a data gap, an ambiguous drift pattern)
are common, realistic issues in any real-world IoT sensor fleet. The specific values,
device IDs, and timestamps are all generated, reproducible, and safe to publish.

Re-running the generator produces byte-identical output every time (fixed random seed),
so the pipeline's behavior can be verified against a known, documented set of injected
issues rather than against an opaque dataset.

## Project goals

- Demonstrate a realistic, defensible approach to sensor data quality: detect issues,
  distinguish *fixable bugs* from *genuinely ambiguous signals*, and never silently
  delete or average away uncertainty.
- Build it local-first: the full core pipeline runs on a laptop with no AWS account
  and no cost, before any cloud integration is considered.
- Treat an optional AWS path (S3 → Glue → Athena) as a small, cost-gated extension,
  not the point of the project. Every cloud resource is explicitly costed and
  approved before it's created, and none has been created yet.

## Quick start

```bash
# 1. Clone and set up
git clone https://github.com/<your-username>/aws-sensor-data-quality-pipeline.git
cd aws-sensor-data-quality-pipeline
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

# 2. Generate the synthetic sample data (deterministic -- safe to re-run anytime)
python scripts/generate_sample_data.py

# 3. Run the full pipeline: ingest -> validate -> transform -> write bronze/silver/gold
python scripts/run_local_pipeline.py

# 4. Run the test suite (24 tests: unit + end-to-end integration)
pytest -v
```

Steps 1 through 3 are implemented and verified, run end to end on a clean machine,
not just in development. Step 3 prints a full reconciliation report (original,
quarantined, corrected, duplicate, and valid record counts) and writes real Parquet
files under `output/bronze/`, `output/silver/`, and `output/gold/`. Step 4 runs 24 tests,
verified on a local Windows machine and on GitHub Actions (Linux). The same suite runs
automatically on every push via `.github/workflows/tests.yml`.

## Known gaps and open issues

Stated plainly so the repo never claims more than the code does.

- **Gap detection is not implemented.** The synthetic data deliberately contains a clean
  2-day outage on `DEV-04`, but no validation rule detects missing time intervals yet.
- **The EC drift on `DEV-03` is not flagged.** It stays inside the configured plausible
  range, so no current rule marks it for review.
- **Null readings are not flagged.** A `value` that fails numeric casting becomes NaN and
  passes every range check silently.
- **Test warnings.** `pytest` passes but reports a NumPy `DeprecationWarning` ("generic
  unit for timedelta") from `transform.py`. It reproduces on both Windows and Linux with
  pandas 2.3.3, and is under investigation. It does not affect results.

## A note on AWS costs

If and when the optional AWS phase is implemented, **no cloud resource is created by
default.** Every deployment step requires explicit review of estimated cost before
anything is provisioned, and a cleanup procedure is documented alongside it. See
`docs/cost_estimate.md` once Phase 6 lands.
