# Data Dictionary & Contract

**Status: synthetic data, deterministic generator.** This project does not use any real
company's dataset. The problem *shapes* (duplicates, unit bugs, a stuck sensor, a gap,
an ambiguous drift) are inspired by common real-world IoT sensor fleet issues, but every
device ID, value, and timestamp below is generated by `scripts/generate_sample_data.py`
with a fixed random seed, fully reproducible, nothing borrowed from any external source.

## `sensor_readings` (bronze layer input)

| Field | Type | Required | Notes |
|---|---|---|---|
| `device_id` | string | yes | Business key component. Format `DEV-XX`. |
| `timestamp` | string → datetime | yes | Expected ISO 8601 `YYYY-MM-DD HH:MM:SS`. One device in the synthetic set deliberately emits a different format, to exercise the validation path. |
| `sensor_type` | string | yes | One of `soil_moisture`, `soil_temp`, `ec`, `humidity`. |
| `value` | float | yes | Unit depends on `sensor_type` (see ranges below). May be null (explicit missing reading) or absent entirely (gap, see Stage 3D). |
| `unit` | string | yes | Declared unit for this reading. Validated against the expected unit per `sensor_type`; a mismatch (e.g. `F` where `C` is expected) is a **unit inconsistency**, not an invalid value. |
| `source_file` | string | yes, added at ingestion | Ingestion metadata, not part of the raw input. |
| `ingested_at` | datetime | yes, added at ingestion | Ingestion metadata. |

**Business key / duplicate definition:** `(device_id, timestamp, sensor_type)`. A true
duplicate is a *full row match* on top of this key: same value, same unit. Two rows
sharing the key but with *different* values are **not** silently deduplicated; they are
flagged as a conflicting-reading anomaly, since collapsing them would discard real
information about a possible retransmission-with-correction or a genuine sensor race
condition.

**Permitted ranges (configurable, declared explicitly, not assumed to be scientifically
authoritative):**

| `sensor_type` | Unit | Plausible range | Hard physical bound |
|---|---|---|---|
| `soil_moisture` | `%` (VWC) | 0–70 typical | 0–100 (cannot be outside this) |
| `soil_temp` | `C` | 5–35 typical | no hard bound enforced, flagged only if implausible |
| `ec` | `uS_cm` | 200–3000 typical | ≥ 0 |
| `humidity` | `%` | 20–100 typical | 0–100 (cannot be outside this) |

A reading outside the **hard physical bound** is an invalid measurement (quarantined
value, flagged, original preserved). A reading outside the **plausible range** but inside
the hard bound is an anomaly for review, not an automatic rejection. This is the
duplicate-vs-anomaly distinction from the FYTA-style analysis applied generically here.

**Expected sampling interval:** 15 minutes, per device. Used by the gap-detection logic
in Stage 3D. This is declared, not inferred, so it's explicit and auditable rather than a
guess baked into code.

## `context_events` (watering / fertilizing log)

| Field | Type | Required | Notes |
|---|---|---|---|
| `device_id` | string | yes | Links to `sensor_readings.device_id`. |
| `event_timestamp` | datetime | yes | |
| `event_type` | string | yes | `watering` or `fertilizing`. |
| `event_text` | string | no | Free-text note, small closed vocabulary by design. |

## Known, deliberately-injected synthetic issues (for the validation suite to catch)

1. **Exact duplicate rows** on `DEV-05`: tests the duplicate-key rule.
2. **A unit mismatch** on `DEV-02` (temperature reported in `F` while declared unit elsewhere is `C`): tests unit-consistency validation.
3. **A malformed-timestamp batch** on `DEV-07` (different string format): tests the ingestion parser's fallback/reject path.
4. **Physically impossible values** on `DEV-05` (moisture below 0%): tests hard-bound validation and quarantine, not silent deletion.
5. **A stuck sensor** on `DEV-06` (identical value repeated for a long run): tests the flatline/run-length detector.
6. **A clean 2-day gap** on `DEV-04`: tests gap detection against the declared sampling interval, distinct from a null value.
7. **A plausible-but-unusual drift** on `DEV-03` (EC rising smoothly over several days): intentionally **not** auto-corrected; must surface as a flagged anomaly for manual review, exercising the "don't silently resolve ambiguity" rule end to end.
